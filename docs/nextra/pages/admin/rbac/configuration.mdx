# RBAC 权限配置指南

> 管理员如何配置和管理 RBAC 权限系统

本文档面向**系统管理员**和**配置人员**,介绍如何配置和管理 RBAC 权限系统。

开发者请查看: [RBAC 实现指南](/admin/rbac/implementation)

## 🎯 系统概述

### 什么是 RBAC?

**RBAC** (Role-Based Access Control, 基于角色的访问控制) 是一种权限管理模型:

```
用户 (User) → 角色 (Role) → 权限 (Permission) + 菜单 (Menu)
```

- **用户** 可以拥有多个**角色**
- **角色** 可以拥有多个**权限**和**菜单**
- **权限** 控制可以执行哪些操作 (Server Actions)
- **菜单** 控制可以访问哪些页面

### 核心特性

- **用户-角色多对多**: 一个用户可以有多个角色
- **角色-权限多对多**: 一个角色可以有多个权限
- **角色-菜单多对多**: 一个角色可以访问多个菜单
- **权限树形结构**: 支持多层级权限组织
- **菜单树形结构**: 支持多层级菜单导航
- **通配符支持**: Action 路径支持 `*` 和 `**` 通配符
- **动态验证**: Server Actions 中自动验证权限

### 5 分钟快速配置示例

假设要给「内容编辑」角色配置「文章管理」权限:

```
1. 创建权限
   - 名称: 文章管理
   - Actions: ["/admin/actions/article/*"]
   
2. 创建菜单
   - 名称: 文章管理
   - URL: /admin/articles
   
3. 创建角色
   - 名称: 内容编辑
   
4. 为角色分配权限
   - 勾选「文章管理」权限
   
5. 为角色分配菜单
   - 勾选「文章管理」菜单
   
6. 为用户分配角色
   - 选择用户
   - 勾选「内容编辑」角色
```

完成!该用户现在可以访问文章管理页面并执行相关操作。

## 🔐 权限管理

### 访问权限管理页面

路径: `/admin/rbac/permissions`

### 创建权限组(顶级权限)

1. 点击 **Create** 按钮
2. 填写权限信息:
   - **Name**: 系统管理
   - **Parent Permission**: (留空 - 顶级权限)
   - **CRUD Category**: Unclassified
   - **Permission Level**: Other
   - **Actions**: (留空 - 分组权限不需要 Actions)
   - **Enabled**: Yes
   - **Sort**: 0

### 创建子权限(具体权限)

1. 点击 **Create** 按钮
2. 填写权限信息:
   - **Name**: 用户管理
   - **Parent Permission**: 系统管理 ⬇️ 选择父权限
   - **CRUD Category**: Read (根据功能选择)
   - **Permission Level**: Bullet
   - **Actions**: `["/admin/actions/rbac/user/*"]`
   - **Enabled**: Yes
   - **Sort**: 10

### Actions 配置详解

**Actions** 字段定义了此权限可以访问的 Server Action 路径。

#### 配置方式

| 配置方式 | 示例 | 说明 | 使用场景 |
|---------|------|------|---------|
| **精确路径** | `/admin/actions/user/create` | 只允许此特定操作 | 细粒度权限控制 |
| **单层通配** | `/admin/actions/user/*` | 允许 user 下的所有直接操作 | 模块级权限 推荐 |
| **多层通配** | `/admin/actions/**` | 允许所有操作 | ⚠️ 慎用(权限过大) |

#### 示例权限树

```
系统管理 (sys-manage)
├── 用户管理 (sys-manage-users)
│   ├── actions: ["/admin/actions/rbac/user/*"]
│   ├── category: Read
│   └── level: Bullet
│
├── 角色管理 (sys-manage-roles)
│   ├── actions: ["/admin/actions/rbac/role/*"]
│   ├── category: Read
│   └── level: Bomb
│
└── 权限管理 (sys-manage-permissions)
    ├── actions: ["/admin/actions/rbac/permission/*"]
    ├── category: Read
    └── level: Grenade
```

### CRUD Category 说明

| 类别 | 值 | 说明 | 适用场景 |
|------|---|------|---------|
| **Create** | 0 | 创建权限 | 添加数据 |
| **Read** | 1 | 读取权限 | 查看数据 |
| **Update** | 2 | 更新权限 | 编辑数据 |
| **Delete** | 3 | 删除权限 | 删除数据 |
| **Import** | 4 | 导入权限 | 批量导入 |
| **Unclassified** | 5 | 未分类 | 分组或其他 |

### Permission Level 说明

| 级别 | 值 | 说明 | 图标 |
|------|---|------|------|
| **Grenade** | 0 | 手榴弹(高危) | 🎯 |
| **Bomb** | 1 | 炸弹(危险) | 💣 |
| **Bullet** | 2 | 子弹(一般) | 🔫 |
| **Knife** | 3 | 刀(低危) | 🔪 |
| **Other** | 4 | 其他 | 📦 |

## 👥 角色管理

### 访问角色管理页面

路径: `/admin/rbac/roles`

### 创建角色

1. 点击 **Create** 按钮
2. 填写角色信息:
   - **Name**: 内容编辑
   - **Remark**: 负责内容的创建和编辑
   - **Enabled**: Yes
   - **Sort**: 10
3. 点击 **OK** 保存

### 为角色分配权限

1. 在角色列表中找到「内容编辑」角色
2. 点击 **Assign Permissions** 按钮
3. 在弹窗中勾选需要的权限:
   - 内容管理
   - 内容管理 → 文章管理
   - 内容管理 → 文章管理 → 创建文章
   - 内容管理 → 文章管理 → 编辑文章
4. 点击 **OK** 保存

#### 权限继承规则

- 勾选父权限,自动包含所有子权限
- 取消勾选父权限,自动取消所有子权限
- 支持部分勾选(只选择部分子权限)

### 为角色分配菜单

1. 在角色列表中找到「内容编辑」角色
2. 点击 **Assign Menus** 按钮
3. 在弹窗中勾选需要的菜单:
   - 内容管理
   - 内容管理 → 文章管理
   - 内容管理 → 分类管理
4. 点击 **OK** 保存

#### 菜单显示规则

- 只显示已分配的菜单
- 父菜单需要同时勾选才能显示层级
- 支持隐藏某些子菜单

## 👤 用户管理

### 访问用户管理页面

路径: `/admin/rbac/users`

### 为用户分配角色

1. 找到目标用户
2. 点击 **Assign Roles** 按钮
3. 在弹窗中勾选角色:
   - 内容编辑
   - 审核员 (可多选)
4. 点击 **OK** 保存

### 验证配置

1. 点击用户的 **View Details**
2. 查看 **RBAC Roles** 字段
3. 应该显示: `[内容编辑, 审核员]`

### Better Auth 角色 vs RBAC 角色

| 字段 | 类型 | 用途 | 示例值 |
|------|------|------|--------|
| `role` | String | Better Auth 基础角色 | `admin`, `user` |
| `roles` | Array | RBAC 角色 UUID 数组 | `["role-uuid-1", "role-uuid-2"]` |

两者共存,互不冲突:

- **`role`**: 用于基础权限判断(如是否可访问后台)
- **`roles`**: 用于细粒度权限控制

## 📊 常见场景配置

### 场景 1: 内容管理系统

**需求**:
- 作者: 可以创建和编辑文章
- 编辑: 可以创建、编辑、删除文章,查看评论
- 管理员: 拥有所有权限

**权限配置**:

```
内容管理
├── 文章管理
│   ├── 创建文章 → ["/admin/actions/article/create"]
│   ├── 编辑文章 → ["/admin/actions/article/update"]
│   ├── 删除文章 → ["/admin/actions/article/delete"]
│   └── 发布文章 → ["/admin/actions/article/publish"]
└── 评论管理
    ├── 查看评论 → ["/admin/actions/comment/list"]
    └── 删除评论 → ["/admin/actions/comment/delete"]
```

**角色配置**:

| 角色 | 权限 |
|------|------|
| 作者 | 创建文章、编辑文章 |
| 编辑 | 文章管理(全部)、查看评论、删除评论 |
| 管理员 | 所有权限 |

### 场景 2: 电商系统

**需求**:
- 客服: 可以查看和处理订单
- 财务: 可以查看订单、退款、导出数据
- 运营: 可以管理商品

**权限配置**:

```
订单管理
├── 查看订单 → ["/admin/actions/order/list", "/admin/actions/order/detail"]
├── 处理订单 → ["/admin/actions/order/process"]
├── 退款 → ["/admin/actions/order/refund"]
└── 导出订单 → ["/admin/actions/order/export"]

商品管理
├── 查看商品 → ["/admin/actions/product/list"]
├── 上架商品 → ["/admin/actions/product/publish"]
└── 下架商品 → ["/admin/actions/product/unpublish"]
```

**角色配置**:

| 角色 | 权限 |
|------|------|
| 客服 | 查看订单、处理订单 |
| 财务 | 查看订单、退款、导出订单 |
| 运营 | 商品管理(所有子权限) |

### 场景 3: 多租户 SaaS

**需求**:
- 租户管理员: 管理本租户的用户和数据
- 超级管理员: 管理所有租户

**实现方式**:

在数据层面添加租户隔离,在 RBAC 基础上:

```javascript
// 在 Server Actions 中检查租户
export async function getDataListAction(params) {
  const session = await auth.api.getSession();
  
  // 非超级管理员只能看本租户数据
  if (session.user.role !== 'super_admin') {
    params.whereJson.tenant_id = session.user.tenant_id;
  }
  
  // 继续查询...
}
```

## 最佳实践

### 1. 权限设计原则

#### 最小权限原则

用户只拥有完成工作所需的最小权限。

```
好的设计:
用户管理
├── 查看用户
├── 创建用户
├── 编辑用户
└── 删除用户

❌ 不好的设计:
用户管理  # 粒度太粗,无法细分权限
```

#### 语义化命名

权限和角色名称应清晰表达功能。

```
好的命名:
"用户管理"、"创建文章"、"导出订单"

❌ 不好的命名:
"UM"、"做某事"、"权限1"
```

#### 分层设计

使用树形结构组织权限,便于管理。

```
系统管理
├── 用户管理
│   ├── 查看用户
│   ├── 创建用户
│   └── 删除用户
└── 角色管理
    ├── 查看角色
    └── 分配权限
```

### 2. 通配符使用建议

#### 推荐: 精确路径或单层通配

```javascript
// 精确控制
actions: ["/admin/actions/user/create"]

// 模块级控制(推荐)
actions: ["/admin/actions/user/*"]
```

#### ⚠️ 谨慎使用: 多层通配

```javascript
// 权限范围太大
actions: ["/admin/actions/**"]

// 全局通配(危险)
actions: ["/**"]
```

### 3. 角色设计建议

#### 职责清晰

每个角色对应一个明确的职责。

```
好的角色:
- 超级管理员: 拥有所有权限
- 用户管理员: 只管理用户
- 内容编辑: 只管理内容
- 只读用户: 只有查看权限

❌ 不好的角色:
- 张三的角色
- 李四的角色
# 为每个用户创建单独角色
```

#### 避免角色爆炸

通过组合多个角色实现复杂权限,而不是创建大量单一角色。

### 4. 安全建议

#### 保护 admin 角色

- 系统禁止删除 admin 角色
- 普通用户不能给自己分配 admin 角色
- admin 角色自动拥有所有权限

#### 审计日志

- 记录所有权限相关操作
- 记录角色分配变更
- 记录权限配置变更

#### 定期审查

- 定期检查用户权限
- 删除不必要的授权
- 检查使用通配符的权限

## ❓ 常见问题

### Q1: 用户同时有多个角色时,权限如何计算?

**A**: 取**并集**。用户拥有所有角色的全部权限。

```javascript
// 用户 A 的角色
roles: ["role-uuid-1", "role-uuid-2"]

// 角色 1 的权限
role1.permission: ["perm-a", "perm-b"]

// 角色 2 的权限
role2.permission: ["perm-b", "perm-c"]

// 用户 A 的最终权限(并集)
finalPermissions: ["perm-a", "perm-b", "perm-c"]
```

### Q2: Better Auth 的 `role` 字段和 RBAC 的 `roles` 字段有什么区别?

**A**:

- `role`: Better Auth 的基础角色,只有 `admin` 和 `user`
- `roles`: RBAC 的角色列表,支持多个自定义角色

两者共存,互不冲突。

### Q3: admin 角色有什么特殊性?

**A**:

- `admin` 角色自动拥有**所有权限**
- 不需要配置权限和菜单
- 可以访问所有页面和操作
- 系统保留角色,不可删除

### Q4: 通配符 `*` 和 `**` 有什么区别?

**A**:

- `*`: 只匹配一层路径
- `**`: 匹配任意层级

示例:

```javascript
"/admin/actions/user/*"
// 匹配: /admin/actions/user/create
// 不匹配: /admin/actions/user/role/assign

"/admin/actions/**"
// 匹配: /admin/actions/user/create
// 匹配: /admin/actions/user/role/assign
```

### Q5: 如何调试权限问题?

**A**:

1. 检查用户的角色: 访问 `/admin/rbac/users`,查看用户详情
2. 检查角色的权限: 访问 `/admin/rbac/roles`,查看角色的权限列表
3. 检查 Action 路径: 在浏览器控制台查看 Network 请求
4. 查看权限匹配日志: 在 Server Action 中添加日志
